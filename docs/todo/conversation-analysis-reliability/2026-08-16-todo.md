触发：同日两次线上失败——豆包流式 `PrematureCloseException` 后 JDBC 回滚盖住原异常；AI 已成功但 `error_point` 超长导致 INSERT 失败，MyBatis 原文出现在分析页。

## 总判断

当前 Stage 2 **默认走流式**，只为前端预览服务；网络抖动没有重试，分批并发偏高，超时把「整段生成时限」和「HTTP 无数据超时」绑在同一个 `120s` 上。失败路径把 `ex.getMessage()` 原样推给 SSE，REST 全局异常处理管不到这条链路。

原则：

1. 只在有明确产品收益的地方用流式，其余走非流式。
2. 临时 I/O 与解析失败分开重试，且总耗时必须落在 SSE 10 分钟以内。
3. 用户只看到短中文；SQL、文件路径、供应商堆栈只打日志。

## P0：减少非必要流式 + 失败对用户不可见

### 1. 整理并收紧流式调用

- [x] 以本文件清单为真源，代码注释 / 日志标明每个 LLM 调用是 stream 还是 chat。
- [x] Stage 2 明确策略：流式只服务前端预览；预览不是正确性前提。
- [x] 评估「先非流式、需要预览再流式」或「仅单批/短文本流式、分批一律非流式」。分批并发时流式收益低、断流风险高，优先砍分批流式。
- [x] Stage 1 / Stage 3 / 中文 Review 保持非流式，禁止新增长耗时流式。

验收：能指出每一处 LLM 调用的方式与理由；超过 `batch-threshold` 的分析不再默认打满流式连接。

### 2. SSE 失败不得把内部异常推到前端

现状：`ConversationAnalysisStreamService` 在虚拟线程里 `ConversationAnalysisProgress.error(ex.getMessage())`，绕过 `GlobalExceptionHandler`。REST 未预期异常返回「服务暂时不可用」，SSE 却把 MyBatis SQL、本机 mapper 路径、JDBC 列名推到进度条和详情页「分析未完成」。`saveFailed` 还把同一段写入 `conversation_analysis.error_message`。

- [x] SSE `ERROR` 事件只发短中文（如「分析失败，请稍后重试」「保存分析结果失败，请重试」）。
- [x] 原始异常只打服务端日志，可带 `analysisId`。
- [x] `saveFailed` 写入用户可读摘要，截断长度保持现有 2000，但不存 SQL / 文件路径。
- [x] `BadRequestException` 等已面向用户的文案可以透出；`DataAccessException` / `PersistenceException` 必须映射。
- [x] 前端继续渲染 `errorMessage`，但契约改为用户文案，不再依赖前端过滤。

验收：复现 `error_point` 超长或 JDBC 回滚时，页面没有 SQL、路径、列名；日志仍能定位根因。

### 3. 落库失败不得毁掉已成功的 AI 结果（与泄露同源）

- [x] `error_point` 落库前截断到列长（DDL `VARCHAR(500)`；测试库 `schema-test.sql` 已对齐为 500）。
- [x] 其它 VARCHAR（`problem_types`、`point_id`、`analysis_id`）同样防御。
- [x] `analyzeAndPersist` 不要用一个 `@Transactional` 包住整个 `pipeline.run()`。先无事务跑 AI，成功后再短事务插入；失败事务不得把 JDBC 回滚异常盖住 AI 原异常。

验收：超长 `error_point` 能保存（截断或加宽后）；AI 失败时日志和前端都能看到 AI 原因，而不是 `Communications link failure during rollback`。

## P1：Stage 2 重试、分批与超时

### 4. 流式 `onError` 覆盖临时 I/O 重试

`GRAMMAR_PARSE_MAX_ATTEMPTS = 2` 只覆盖 JSON 解析失败和「异常结束」。不覆盖：

- `PrematureCloseException` / `Connection reset by peer`
- `ReadTimeoutException`
- `ResourceAccessException`
- 其它临时 I/O

- [x] `streamJsonText` 的 `onError` 判定可重试后：立即改走 `fetchGrammarJsonSync`（与现有「未正常结束」回退对齐）。
- [x] 不可重试（4xx、鉴权、内容审核、业务 `BadRequestException`）不重试。
- [x] 重试次数与退避单独配置，不要复用 `langchain4j.open-ai.chat-model.max-retries: 3` 的长超时乘积。

验收：单次流式断流不再使整场分析立刻失败；日志能看到 attempt 与是否回退非流式。

### 5. 失败批次可单批重试（并发度不改）

现状（已改）：`batch-threshold=15`，`batch-size=5`，`batch-concurrent-limit=5`（本期不降并发）。分批非流式；失败或尚未开始的批次再试一次，已成功批次保留。

- [x] **并发度不修改**：保持 `batch-concurrent-limit=5`（可配），本期不降到 2。
- [x] 只重试失败批次，已成功结果保留。
- [x] 失败批次用非流式重试（与分批主路径一致）。
- [x] 某批失败时取消尚未开始的批次；已在飞的请求要能记录 `analysisId` + `batchNum`。

验收：并发上限仍为 5；1 批失败后其余已成功批次结果仍可用，失败与未开始批次会再试一次。

### 6. 拆开「流式总时限」和「HTTP 无数据超时」

现状（已改）：三个含义不再共用 `AI_TIMEOUT_MS`。

- [x] HTTP 读超时：无数据多久断开（`AI_HTTP_READ_TIMEOUT=45s`）。
- [x] 流式墙钟时限：整段生成上限（`AI_STREAM_WALL_CLOCK_TIMEOUT=5m`，小于 SSE 10 分钟）。
- [x] 非流式单次超时单独配置（`AI_CHAT_TIMEOUT=60s`）。
- [x] 配置名写进 `application.yml` / `.env.example`。

验收：持续出 token 的长流不会在 120s 被 `latch.await` 误杀；对端卡住仍能在读超时内失败。

### 7. 缩短非流式重试总耗时

现状（已改）：非流式单次 60s，LangChain4j `max-retries=1`（一层 HTTP 尝试）；分批失败再由业务层重试一次。

最坏路径（`ConversationAnalysisTimeoutBudget`）：

```text
Stage2 分批墙钟 ≈ 并发波次 × chatTimeout × 失败批次重试次数
全链路 ≈ Stage2 + Stage1 + 中文 Review + Stage3（各 1 × chatTimeout）
20 句：1 波 × 60s × 2 + 3×60s = 5 分钟
50 句：2 波 × 60s × 2 + 3×60s = 7 分钟
单批流式：5m 墙钟 + 60s 回退 + 3×60s = 8 分钟
均 < SSE 10 分钟
```

- [x] 非流式：更短单次超时 + 更少次数（60s × LangChain4j 1 次；分批业务层再 1 次）。
- [x] 分批场景按「波次 × 超时 × 重试」估算最坏时间，必须明显小于 10 分钟，留出 Stage 1/3 和落库。
- [x] LangChain4j `max-retries` 与业务层重试不要叠乘；HTTP 层只保留 1 次尝试。

验收：文档或测试给出最坏路径耗时上限；单阶段重试不会单独吃掉大部分 SSE 窗口。

## P2：请求级关联日志

内部请求日志需能把一次分析的所有 LLM 调用串起来，区分「同一次分析里豆包超时、千问断流」。不引入 Jaeger/Zipkin；前端不展示这些字段。

每次 LLM 调用（含流式回退、解析重试、落库）打一条：

```text
llm_call analysisId={} stage={} model={} attempt={} durationMs={} result={}
```

| 字段 | 说明 |
| --- | --- |
| `analysisId` | SSE 入口 UUID；MDC 同步写入，分批虚拟线程复制 |
| `stage` | `separation` / `grammar` / `chinese-review` / `summary` / `persist` |
| `model` | 配置 id（如 `doubao-seed` / `qwen3.6-plus`）；Stage1 用分离模型名 |
| `attempt` | 从 1 计（流式失败后的 chat 回退为 2） |
| `durationMs` | 墙钟 |
| `result` | 成功为 `ok`；失败为根因异常短名（如 `PrematureCloseException`），不含 SQL |

仅在有用时追加：

- `batch=2/5`：分批 Stage2，禁止 `0/0`
- `mode=stream` / `mode=chat`：仅 Stage2 区分流式与 chat 回退

不记录：`provider`、拆开的 `outcome`+`rootCause`、非分批的 `batchNum`。

- [x] `ConversationAnalysisCallLog` 统一格式；Helper / Pipeline / 中文 Review / 落库各打一条。
- [x] SSE 虚拟线程写入 MDC `analysisId`，`finally` 清理；分批 worker 复制父线程 MDC。
- [x] 禁止只打供应商 SDK 默认 request/response 而不带 `analysisId`。
- [x] 前端不展示这些字段。

验收：用一次 `analysisId` grep 能列出该次全部 LLM 调用的 stage、批次、attempt、耗时和失败原因。
